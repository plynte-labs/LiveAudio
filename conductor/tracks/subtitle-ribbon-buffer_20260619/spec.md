# Specification: Vertical Ribbon Subtitle Buffer for OBS Overlay

## 1. Goal

Add subtitle display MODES beyond the current single-line behavior to the OBS browser-source overlay (`liveaudio/assets/subtitulos_obs.html`), so the overlay can stack the N most-recent subtitles vertically as a "ribbon"/tape. Each stacked line ages out independently with smooth per-line enter/exit animation, and the number of simultaneously visible lines is configurable.

**The shipped DEFAULT is now `adaptive` (LOCKED decision, 2026-06-19).** Per the maintainer, the stack must engage ONLY when subtitles start to accumulate / overlap (ASR emitting faster than one-line-at-a-time pacing, or a backlog catch-up). When the flow is one subtitle at a time, the overlay MUST stay single-line exactly as today. The point is to avoid an oversized block of text on screen — the ribbon is a relief valve for bursts, not a permanent multi-line layout. Three modes are defined:
- `single`: always one line — today's behavior, now the explicit opt-OUT for purists.
- `ribbon`: always stacked up to N.
- `adaptive` (DEFAULT): single under normal pacing, auto-expands to a bounded ribbon on accumulation, then collapses back.

Because adaptive is VISUALLY IDENTICAL to today under normal one-at-a-time pacing (it never stacks unless the queue backs up or a catch-up burst arrives), making it the default is the intended, safe change: existing OBS browser sources keep looking the same in steady speech, and only gain stacking during the exact bursts that previously flashed text past too fast or dropped lines. `?mode=single` fully restores the legacy one-line-replace behavior for anyone who wants it.

Today the overlay shows exactly ONE subtitle at a time: `showSubtitle()` (`subtitulos_obs.html:409-549`) clears the shared timers (`clearTimeout(hideTimeout)` / `clearTimeout(cleanupTimeout)`, `:416-417`), locates the prior box via `container.querySelector('.sub-box')` (`:420`), removes it with `container.removeChild(existing)` (`:422`), nulls the reference for GC (`:423`), then appends the new box (`:507`). The hide fires at 5000ms (`:510-548`) and the node is removed 650ms later (`:539-546`) — these timings were retuned by Track C and are REUSED as-is. The ribbon render branch must NOT remove the prior box; it must append and let each box self-expire on its OWN per-line timer.

Single-line behavior is fully preserved as the explicit `single` mode, and adaptive degrades to it under normal pacing: existing OBS browser-source URLs (e.g. `?style=neon&port=8765`) keep working with no visible change in steady speech, and no GUI change is required.

## 2. Requirements

### REQ-1 (P0): New `ribbon` render branch that stacks instead of replaces
- Introduce a client display-mode switch with three values: `single` (current behavior), `ribbon` (always-stacking), and `adaptive` (default — single that promotes to the ribbon render branch on accumulation, see REQ-10).
- In the ribbon render branch, `showSubtitle()` MUST NOT clear the shared timers nor call `container.removeChild(existing)` on the prior `.sub-box` (`subtitulos_obs.html:416-417`, `:420-424`). It MUST append the new box while leaving older still-living boxes in place.
- In `single` mode, behavior MUST be byte-for-byte equivalent to today: one `.sub-box` at a time, shared timers cleared (`:416-417`), prior box removed before append (`:420-424`).
- The per-line lifetime is REUSED, not changed: each box still hides at 5000ms (`subtitulos_obs.html:510`) and is removed 650ms after (`subtitulos_obs.html:539-546`). These are the Track-C-retuned values and MUST NOT be re-derived here.

### REQ-2 (P0): Per-line independent lifetime in the ribbon render branch
- Each visible line in the ribbon render branch MUST own its OWN hide timer and cleanup timer. The current implementation uses module-level singletons `let hideTimeout` and `let cleanupTimeout` (`subtitulos_obs.html:263-264`) plus `clearTimeout(hideTimeout)` / `clearTimeout(cleanupTimeout)` at the top of every `showSubtitle()` call (`subtitulos_obs.html:416-417`). That single-timer model MUST be replaced (in the ribbon branch) by per-line timers stored ON each box (e.g. `sub._hideTimer` / `sub._cleanupTimer`), so that appending line B does NOT cancel line A's expiry.
- When a line expires, only THAT line transitions out (`hiding` class, `subtitulos_obs.html:511-512`) and only THAT line's node is removed (`subtitulos_obs.html:539-546`); sibling lines are untouched.
- GC discipline from the predecessor track MUST be preserved per line: each expired box is removed via `removeChild` and the per-line timer ids nulled (mirrors `subtitulos_obs.html:420-424` / `:539-546` and the `subtitle-style-system_20260509` memory-leak fix).
- `onSubtitleComplete()` (`subtitulos_obs.html:372-375`) currently toggles the single `isShowing` flag and pumps the queue; in the ribbon branch this MUST NOT gate on `isShowing` (see REQ-7 / decision 1.3).

### REQ-3 (P0): Configurable maximum visible lines with clamp
- A maximum visible-line count governs the ribbon. When appending a new line would exceed the maximum, the OLDEST visible line is evicted immediately (forced exit + removal) so the stack never exceeds the configured cap.
- New config key `subtitle_ribbon_max_lines`, default `3`, clamped to the inclusive range `1..8`. Added to `DEFAULT_CONFIG` (`liveaudio/utils/config.py:59-88`) and validated/clamped in `_normalize_config` via the existing `_clamp_number(...)` helper (`:91-100`) with `cast=int`, mirroring the `cpu_threads` int-clamp at `:136` and the `subtitle_max_live_delay_sec` float-clamp at `:195-197`.
- A value of `1` in the ribbon branch is functionally equivalent to single mode (only one line ever visible) but still uses the per-line timer path.

### REQ-4 (P0): New `subtitle_display_mode` config key (default `adaptive`) — LOCKED
- New config key `subtitle_display_mode` with values `single | ribbon | adaptive`, **default `adaptive`** (LOCKED 2026-06-19, was `single`). Added to `DEFAULT_CONFIG` (`liveaudio/utils/config.py:59-88`).
  - `single`: legacy behavior — one line, replace-on-new. Explicit opt-OUT for purists.
  - `ribbon`: always stack up to `subtitle_ribbon_max_lines`.
  - `adaptive` (DEFAULT): single-line under normal pacing; auto-engages the bounded ribbon on accumulation and collapses back when caught up (see REQ-10). This is the maintainer's preferred behavior and the shipped default.
- A new validation set `VALID_SUBTITLE_DISPLAY_MODES = {"single", "ribbon", "adaptive"}` added alongside the existing `VALID_SUBTITLE_STYLES` (`:55`) and `VALID_BACKLOG_POLICIES` (`:56`).
- `_normalize_config` MUST reject unknown values and fall back to the DEFAULT `adaptive` (pattern matches the existing `subtitle_backlog_policy` check against `VALID_BACKLOG_POLICIES` at `:191-193`, which falls back to `DEFAULT_CONFIG[...]`). Because the fallback is `DEFAULT_CONFIG["subtitle_display_mode"]`, the fallback automatically tracks the locked default — do NOT hard-code `"single"` in the normalization branch.

### REQ-5 (P0): URL-param opt-in `?mode=` and `?lines=N` (no GUI required)
- The overlay MUST read `?mode=` and `?lines=` from `window.location.search` using the existing `URLSearchParams` pattern (`subtitulos_obs.html:270`, `:379-380`).
- `?mode=single|ribbon|adaptive` selects the render mode for that browser source; any other / absent value resolves to the config/default `adaptive` (the locked default). `?mode=single` is the explicit legacy opt-out.
- `?lines=N` overrides the max visible lines for that browser source, clamped client-side to `1..8`; absent value falls back to the server/config-provided default or the built-in default of `3`.
- CRITICAL anti-pattern guard: the parsed mode/lines values MUST actually be READ at decision time (in `enqueueSubtitle`/`processQueue`/`showSubtitle`), not merely stored in an unused `let`. The existing `currentStyle` variable (`subtitulos_obs.html:272`) is assigned from `?style=` but NEVER read again (dead variable; style in practice comes from `data.style` in the payload at `:396`). The mode flag MUST NOT repeat this mistake.

### REQ-6 (P1): Server-driven mode hint via payload — DEFERRED (see OD-5 RESOLVED)
- With `adaptive` now the LOCKED default (REQ-4), the config default + URL `?mode=` cover every shipping case, so the optional `engine.py` `display_mode` payload hint is **DEFERRED** out of this track (OD-5 resolved: do not ship now). This keeps `engine.py` and `tests/test_engine.py` UNTOUCHED, shrinking the diff and removing payload-shape churn.
- For reference (if a future GUI toggle needs a live channel): the payload is constructed at `liveaudio/core/engine.py:576-587`; a `display_mode` key would be added there alongside `style` (`:579`), read from `shared_config.get("subtitle_display_mode", "adaptive")` mirroring the `style` read at `:572-574`. The client onmessage handler (`subtitulos_obs.html:386-401`) already ignores unknown payload keys (`data.text` gate at `:395`), so adding `display_mode` later is non-breaking for older overlays.
- Precedence (when later implemented): an explicit URL `?mode=` on the browser source WINS over the payload hint (URL is per-source intent and must stay deterministic for OBS). Payload hint applies only when the URL did not specify a mode.

### REQ-7 (P1): Define ribbon interaction with existing client backpressure
- The existing client backpressure block is `MAX_PENDING_QUEUE = 5` (`subtitulos_obs.html:314`) + `DEBOUNCE_MS = 80` (`:315`) with `enqueueSubtitle` (`:325-336`), `processQueue` (`:338-369`), and `onSubtitleComplete` (`:372-375`). Today `processQueue` is a strict serialization gate keyed by the single `isShowing` flag (`:322`, `:333`, `:344`), and a full queue discards the OLDEST pending item via `pendingQueue.shift()` (`:327-328`).
- In the ribbon render branch the queue MUST become the visible stack rather than a discard buffer: pending lines should surface AS the ribbon (concurrent visible boxes) up to `subtitle_ribbon_max_lines`, instead of being serialized one-at-a-time behind `isShowing` and silently dropped at depth 5.
- `DEBOUNCE_MS` (80ms) pacing SHOULD be preserved in the ribbon branch to avoid visual thrash on bursts; the OPEN DECISION in section 6 records whether debounce stays, is relaxed, or is removed.
- Single mode MUST keep the exact current backpressure semantics (serialize + discard-oldest) with zero behavioral change. Under adaptive-default, the SINGLE-state path of adaptive ALSO keeps these exact semantics until promotion.

### REQ-8 (P1): Stacking direction — newest-on-TOP (RESOLVED)
- LOCKED: NEWEST on TOP, OLDEST on BOTTOM ("arriba el mas reciente, abajo el mas antiguo"). OD-1 RESOLVED — Option A.
- The current layout is bottom-anchored: `body` is `display:flex; flex-direction:column; justify-content:flex-end` (`subtitulos_obs.html:25-36`) and `#subtitle-container` has `width:90%; margin-bottom:50px` (`:38-43`). In a bottom-anchored flex column, naive `appendChild` places the NEWEST box at the BOTTOM.
- DECISION: apply `flex-direction: column-reverse` to the ribbon container (a single CSS rule toggled by a ribbon-active modifier class). This keeps insertion as `appendChild` (cheapest, identical to today) while rendering newest-on-TOP, oldest-on-bottom, growing UPWARD above the existing 50px margin. Isolating the direction to ONE CSS rule makes a later flip to newest-bottom a one-line change with zero JS impact.

### REQ-9 (P0): Backward compatibility under adaptive-default
- LOCKED context: the shipped default is now `adaptive` (REQ-4), NOT `single`. The backward-compat guarantee is therefore reframed: under adaptive-default, existing OBS browser sources with no params are VISUALLY IDENTICAL to today during normal one-at-a-time pacing, because adaptive never stacks unless the pending queue backs up or a catch-up burst arrives. It only stacks during the exact accumulation/catch-up bursts that previously flashed text past too fast or dropped lines at the queue cap. This is the intended, safe change — framed as an improvement that is invisible in steady speech.
- **AC-driven guarantee 1 (normal-pacing identity):** with default config / no params, sending subtitles one at a time with normal gaps MUST render exactly one `.sub-box` at any instant, with the same 5000ms lifetime and the same single-line replace timing as today (no stacking, no visual or timing regression). See AC-15.
- **AC-driven guarantee 2 (explicit legacy restore):** `?mode=single` MUST fully restore the legacy single-line-replace behavior, byte-for-byte (shared-timer clear `:416-417`, removeChild-before-append `:420-424`, serialized backpressure with discard-oldest `:327-328`). See AC-1, AC-11, AC-17.
- Existing OBS browser-source URLs (e.g. `?style=neon`, `?port=8765`) MUST continue to work unchanged; adaptive resolves transparently when no `?mode=` is present.
- All 7 existing style presets (`.style-default` through `.style-typewriter`) MUST render correctly in ALL modes; the ribbon render branch must not assume a single active `.sub-box`.

### REQ-10 (P0): Adaptive engagement — stack only on accumulation (DEFAULT)
- `adaptive` is the LOCKED shipped default. The overlay MUST render single-line under normal pacing and AUTO-ENGAGE the ribbon ONLY when subtitles accumulate, then collapse back to single-line once the backlog drains. Goal: never show an oversized block of text during steady one-at-a-time speech.
- Adaptive is modeled as a TWO-STATE machine (`SINGLE` ⇄ `RIBBON`) layered over the existing enqueue/process path; full state/transition/hysteresis design lives in `plan.md` §1.10–1.12. Summary of the contract:
  - **Promote SINGLE→RIBBON** when, at enqueue time, more than one item is waiting while one is already visible — i.e. `pendingQueue.length > 1` (`subtitulos_obs.html:320`, `:327-328`, `:338-369`) — OR a payload arrives with `is_replay: true` (`liveaudio/core/engine.py:585`). Promotion surfaces the pending items as concurrent visible lines (up to `subtitle_ribbon_max_lines`) instead of serializing + discarding them.
  - **Demote RIBBON→SINGLE** ONLY when the pending queue has fully drained (`pendingQueue.length <= 1`) AND only ONE live `.sub-box` remains AND `is_replay` is no longer arriving, after a short settle window (reuse `DEBOUNCE_MS = 80`, `:315`). The surviving live line MUST NOT flicker or be re-rendered across the transition — demotion only swaps which code path future lines take, it does not touch existing boxes.
- Engagement signal (client-side, primary): the existing pending-queue depth (`pendingQueue`, `:320`). Secondary (server-assisted): the OBS payload backlog/catch-up hints the overlay currently IGNORES — `is_replay` (set when `queue_delay > 1.0`), `catchup_interval_sec`, and `total_delay` (`liveaudio/core/engine.py:583,585-586`). While `is_replay` is true the overlay STAYS in RIBBON so a catch-up burst fills the ribbon rather than flashing past as single lines.
- Hysteresis / anti-flap: promotion is edge-triggered (`> 1`), demotion requires full drain + one live line + the settle window, so the state cannot oscillate at the threshold. See `plan.md` §1.11.
- Per-line timer ownership is the SAME as the ribbon branch (REQ-2): boxes created while in RIBBON own per-line `_hideTimer`/`_cleanupTimer`; a box created while in SINGLE uses the legacy shared-timer path. Transitions MUST NOT orphan or double-remove any in-flight box (design in `plan.md` §1.12).
- Interplay with the engine backlog policy (`subtitle_backlog_policy`, `engine.py:197-213`): adaptive is a CLIENT render decision and does NOT change what the server emits. NOTE the interaction — `live_only` policy returns `is_replay = False` and suppresses emission when `queue_delay > max_delay` (`engine.py:208-209`), so under `live_only` the very backlog that would feed the ribbon may never reach the overlay; adaptive then engages only on raw client-side queue depth. `auto` and `send_all` DO emit `is_replay`, so adaptive's secondary signal is active under those policies (`engine.py:205-206`, `:211-213`).
- The exact accumulation threshold and its `DEBOUNCE_MS` interplay during catch-up bursts are recorded in OD-6 (RESOLVED, with recommendation).
- `single` and `ribbon` modes are unaffected by this requirement (they are non-adaptive by definition).

## 3. Non-Functional Requirements

- NFR-1 (Memory): Ribbon mode MUST NOT leak DOM nodes over a long session. With the cap enforced, the live `.sub-box` count is bounded by `subtitle_ribbon_max_lines` (<= 8). Per-line cleanup MUST mirror the predecessor track's `removeChild` + nullify discipline; node count returns to 0 within ~5350ms of the last subtitle.
- NFR-2 (No flicker): On a burst of subtitles, ribbon entry/exit MUST remain smooth (reuse the unified `--sub-animation-duration` transition at `subtitulos_obs.html:50,62`, now `0.3s` per Track C `:19`); no mid-animation interruption of sibling lines, and no flicker of the surviving line across SINGLE⇄RIBBON transitions.
- NFR-3 (Determinism for OBS): Mode RESOLUTION from the same URL/config MUST be deterministic across browser-source reloads — no reliance on timing or message order to settle into a mode. (Adaptive STATE may transition at runtime by design, but the resolved MODE is fixed at load.)
- NFR-4 (No new network surface): No new WebSocket message TYPE is introduced for mode. Mode rides either the URL or config; the OD-5-deferred payload hint (if ever shipped) would ride the existing per-utterance payload dict broadcast by `_broadcast_msg` (`liveaudio/core/network.py:108-113`), which already forwards any dict unchanged. Adaptive reuses the `is_replay`/`catchup_interval_sec` fields ALREADY present in the payload (`engine.py:585-586`) — no new fields.
- NFR-5 (Single source of truth for validation): `subtitle_display_mode` / `subtitle_ribbon_max_lines` validation lives in `config.py` `_normalize_config` (`:103+`); the client clamp on `?lines=` is a defensive secondary guard, not the authority.
- NFR-6 (Config sync): With OD-5 deferred, NO mode value is mirrored on the Python engine side in this track, so the `VALID_SUBTITLE_STYLES` duplication problem (`engine.py:22` / `config.py:55`) is NOT extended. If a future track ships the payload hint, it MUST import `VALID_SUBTITLE_DISPLAY_MODES` from `config.py` rather than copying it.

## 6. Open Decisions

- **OD-1 (REQ-8) — Stacking direction. RESOLVED: newest-on-TOP (Option A).** The maintainer's literal "arriba el mas reciente, abajo el mas antiguo" is honored. Implementation: `flex-direction: column-reverse` on the ribbon container, keeping `appendChild` insertion and the existing 50px bottom margin (`:42`). Isolated to ONE CSS rule so a later flip to newest-bottom is a one-line change. No further confirmation needed.

- **OD-2 (REQ-3) — Default and ceiling for `subtitle_ribbon_max_lines`. RECOMMENDATION: 3, clamp 1..8 (still open for confirm).** Three lines balances readability against occlusion of the stream; ceiling 8 prevents the ribbon from covering the frame. RECOMMENDATION to ship default 3 / clamp 1..8. Maintainer may prefer a lower ceiling (e.g. 5) for safety on smaller canvases — low-risk, can ship the recommendation and adjust later via config.

- **OD-3 (REQ-7) — Debounce during catch-up bursts. RECOMMENDATION: keep `DEBOUNCE_MS = 80` (still open for confirm).** Preserving the 80ms pacing (`subtitulos_obs.html:315`) avoids visual thrash when ASR emits a burst, and 80ms is fast enough that even a full `is_replay` catch-up fills `subtitle_ribbon_max_lines` (≤8) within ~640ms — imperceptible as "slow". RECOMMENDATION: keep 80ms uniformly (do NOT special-case replay) to keep one pacing rule and avoid a second timing path. Maintainer should confirm whether replay bursts must fill instantly (relax to 0) — only matters if 8 lines in 640ms feels laggy, which is unlikely.

- **OD-4 (REQ-7) — Backpressure depth vs ribbon depth. RECOMMENDATION: decouple (still open for confirm).** Keep `MAX_PENDING_QUEUE = 5` (`:314`) as the transport/pending guard, and let `subtitle_ribbon_max_lines` (default 3) govern VISIBLE depth independently. RECOMMENDATION: decouple — they answer different questions (how much to buffer in transit vs how much to show). Note a subtlety the maintainer should be aware of: with `MAX_PENDING_QUEUE=5` and ribbon cap 3, a >5 burst still discards the oldest PENDING items at the transport layer before they ever become visible — acceptable (those are the stalest lines), but worth confirming the maintainer is fine with transport-level discard during extreme bursts rather than raising `MAX_PENDING_QUEUE`.

- **OD-5 (REQ-6) — Ship the server-driven payload hint now or defer. RESOLVED: DEFER.** With `adaptive` now the LOCKED default, the config default + URL `?mode=` cover every shipping case, so the payload hint adds no value this track and would force payload-shape churn in `tests/test_engine.py`. DECISION: defer all `engine.py` changes; ship URL+config only. `engine.py` and `tests/test_engine.py` are OUT OF SCOPE (section 5). A future GUI-toggle track can add the hint, importing `VALID_SUBTITLE_DISPLAY_MODES` from `config.py` (NFR-6).

- **OD-6 (REQ-4, REQ-10) — Default mode and the adaptive engagement threshold. PARTIALLY RESOLVED.**
  - (a) Default mode — **RESOLVED: `adaptive`.** The shipped default is `adaptive` (LOCKED 2026-06-19). It degrades to single under normal pacing (AC-15), so it is the desired behavior with no steady-state regression. `single` is the explicit opt-out.
  - (b) Accumulation trigger — **RESOLVED (recommendation, low-risk to confirm): engage at `pendingQueue.length > 1` OR `is_replay: true`.** This is the cheapest signal already tracked client-side and the server already emits `is_replay`. Demote on full drain (≤1 pending) + one live line + settle window. Maintainer may tune the `> 1` threshold after seeing it live (e.g. require 2 truly-concurrent live boxes) — isolated to one comparison, trivial to adjust.
  - (c) Debounce during catch-up — ties to OD-3 (RECOMMENDATION: keep 80ms uniformly). Still open for confirm there.
